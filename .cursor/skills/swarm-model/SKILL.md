# 蜂群模型 (Swarm Model)

一种节省上下文窗口的两阶段工作模式，通过任务隔离实现高效开发。

## 核心理念

| 角色 | 职责 | 上下文 |
|------|------|--------|
| **架构师（蜂后）** | 规划、拆解、审核、合并 | 全局视角 |
| **开发者（工蜂）** | 局部执行、输出报告 | 最小必要上下文 |

---

## 阶段一：架构师模式（规划与拆解）

### 触发条件

当收到以下类型需求时，必须进入架构师模式：
- 涉及 3 个以上文件的修改
- 需要跨模块协调的功能
- 用户明确要求"规划"或"拆解"
- 复杂度评估为"非琐碎"的任务

### 架构师职责

```
1. 接收需求 -> 2. 分析复杂度 -> 3. 拆解子任务 -> 4. 生成任务卡片 -> 5. 审核+合并
```

#### 1. 需求分析

- 理解用户的核心目标
- 识别涉及的模块和文件
- 评估任务复杂度

#### 2. 复杂度判断

| 等级 | 特征 | 处理方式 |
|------|------|----------|
| **琐碎** | 单文件、单一功能、< 50行代码 | 直接执行，无需拆解 |
| **中等** | 2-3个文件、有关联的修改 | 轻量拆解，2-3个子任务 |
| **复杂** | 多模块、需要协调、>5个文件 | 完整拆解，生成任务卡片 |

#### 3. 任务拆解原则

- **独立性**：每个子任务可独立完成，不依赖其他子任务的中间状态
- **原子性**：子任务粒度适中，单次执行可完成
- **可验证**：每个子任务有明确的验收标准
- **上下文最小化**：子任务只涉及必要的文件和信息

#### 4. 生成任务卡片

为每个子任务生成标准格式的任务卡片：

```markdown
## 任务卡片 #[编号]

### 上下文边界
- **文件范围**: [明确列出需要读取的文件路径]
- **依赖信息**: [需要了解的最小背景信息]

### 任务目标
[一句话描述这个任务要完成什么]

### 输入
- [必需的数据/状态/参数]

### 预期输出
- [ ] [验收标准1]
- [ ] [验收标准2]

### 约束
- **不读取**: [禁止访问的文件或目录]
- **不修改**: [禁止修改的范围]
- **最大文件数**: [建议 ≤ 5]

### 提示
[可选：执行建议或注意事项]
```

## 阶段二：开发者模式（局部执行）

### 触发条件

当收到任务卡片时，进入开发者模式执行。

### 开发者职责

```
1. 领取卡片 -> 2. 加载最小上下文 -> 3. 局部执行 -> 4. 输出执行报告
```

### 执行规则

| 规则 | 说明 |
|------|------|
| **最小读取** | 只读取任务卡片中指定的文件，不主动探索 |
| **文件限制** | 单次执行读取文件数 ≤ 5 个 |
| **聚焦目标** | 只完成卡片中定义的目标，不做额外修改 |
| **标准输出** | 必须输出执行报告 |

### 执行报告格式

```markdown
## 执行报告 #[任务编号]

### 完成状态
[成功 / 部分完成 / 失败]

### 修改摘要
| 文件 | 操作 | 说明 |
|------|------|------|
| path/to/file.js | 修改 | 添加了xxx功能 |

### 验收清单
- [x] 验收标准1 - 已完成
- [ ] 验收标准2 - 未完成（原因：xxx）

### 遗留问题
[如有未完成的事项，在此说明]

### 备注
[可选：额外的说明或建议]
```

```
用户需求
    │
    ▼
┌─────────────────────────────────────┐
│        架构师模式（蜂后）              │
│  ┌─────────────────────────────┐    │
│  │ 1. 分析需求复杂度            │    │
│  │ 2. 判断：琐碎？→ 直接执行    │    │
│  │ 3. 拆解为独立子任务          │    │
│  │ 4. 生成任务卡片              │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
    │
    ▼ (分发任务卡片)
┌─────────────────────────────────────┐
│        开发者模式（工蜂）              │
│  ┌─────────────────────────────┐    │
│  │ 1. 领取单个任务卡片          │    │
│  │ 2. 加载最小必要上下文        │    │
│  │ 3. 在隔离环境中执行          │    │
│  │ 4. 输出标准化执行报告        │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│        架构师模式（蜂后）              │
│  ┌─────────────────────────────┐    │

│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
    │
    ▼
```

## 使用示例

### 示例1：中等复杂度任务

**用户需求**: "给 GUXY 添加一个深色主题切换功能"

**架构师分析**:
- 涉及文件：CSS变量文件、主题切换UI、状态管理
- 复杂度：中等
- 拆解为 3 个子任务

**任务卡片 #1**: 创建深色主题CSS变量
**任务卡片 #2**: 添加主题切换按钮组件
**任务卡片 #3**: 实现主题状态持久化

### 示例2：琐碎任务

**用户需求**: "修复按钮的 hover 颜色"

**架构师判断**: 单文件、单一功能 → 直接执行（无需拆解）

## 关键原则速查

| 原则 | 架构师 | 开发者 |
|------|--------|--------|
| 任务隔离 | 确保子任务独立 | 不越界执行 |
| 最小上下文 | 精简卡片内容 | 只读指定文件 |
| 标准输出 | 审核执行报告 | 按格式输出 |
| 迭代改进 | 不通过则返工 | 修正后重新提交 |

---

## 注意事项

1. **不要跳过架构师模式**: 即使任务看起来简单，也要先评估复杂度
2. **不要在开发者模式做决策**: 遇到卡片外的问题，返回架构师模式
3. **保持卡片原子性**: 如果子任务仍然复杂，继续拆分
4. **及时合并**: 完成所有子任务后，架构师必须合并结果并交付
